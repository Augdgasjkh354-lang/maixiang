# 0.1.9-r01 支付预检复用：实现、性能与验证记录

## 改动范围

本轮只优化市场与服务报价中的重复支付能力计算，不改变成交顺序、价格、需求扣减、支付规则、日结顺序或存档结构。

- `src/economy/payment.js`：新增短生命周期 `createPaymentCapabilityContext`。一次同步报价搜索内缓存货币阶段/目标比例、粮券余额、小麦余额与保护上限、当日自动换券能力和整数换算所需数据；上下文不挂到 `state`，不跨成交、卖家或游戏日保存。
- `src/systems/consumer-market.js`：`maximumAffordableUnits` 的二分候选仍逐个按原整数规则报价，但不再为每个候选重复扫描家庭生活储备与换券额度。
- `src/systems/services.js`：服务预算保留原先的无上限最大支付值作为二分上界；仅有相同 `maxWheatUnits` 约束的二分搜索复用上下文，避免改变上界或预算语义。
- 普通真实成交继续走 `settleMonetaryPayment`，成功付款、收款、兑换、库存/储备变化后不会沿用旧上下文。没有实现跨卖家缓存，因为同户可同时买卖，且购买食物本身可能改变生活储备可用小麦。

## 性能测量

环境：Node v22.16.0 / Linux x64 / AMD EPYC 9V74。固定状态预热 6 次，随后旧版与新版交替测量各 20 次；每次都从同一快照克隆后只执行一个日结。Node 结果仅代表同环境头less 日结，不代表浏览器或手机帧率。

### 固定活跃经济快照

| 指标 | 0.1.8 | 0.1.9 | 变化 |
| --- | ---: | ---: | ---: |
| 单日日结平均 | 70.658 ms | 51.691 ms | -26.8% |
| 单日日结中位数 | 69.934 ms | 50.684 ms | -27.5% |
| 支付候选报价次数 | 13,673 | 13,673 | 不变 |
| 家庭可支付小麦计算 | 31,207 | 4,633 | -85.2% |
| 自动换券能力计算 | 13,683 | 1,530 | -88.8% |

报价次数保持不变，说明收益来自复用同一搜索中的不变支付能力，而不是减少二分候选、降低家庭数量或近似计算。

### 固定新局

新局没有活跃商业/服务热点。候选报价仍为 94 次，可支付小麦计算仍为 500 次，自动换券能力检查由 94 次降为 6 次。该场景耗时只有约 3–4ms，20 次样本中均值受单次调度尖峰影响，没有报告稳定的耗时收益；本轮收益判断以活跃经济快照为准。

## 等价验证

使用未修改的 0.1.8 与 0.1.9 对同一快照分别结算并逐字段比较结果与完整 state：

- 固定新局：单日结果与完整 state 完全一致。
- 活跃经济快照：小麦、50%混合、全粮券三个阶段，各连续 5 日；共 15 个日结结果与 15 个完整 state 全部逐字一致。
- 边界：余额不足 0 成交、全粮券自动换券后的部分成交、混合阶段兑换成交、同一家庭在同一市场轮次既卖出又买入；结果和完整 state 均与 0.1.8 一致。
- 自动换券部分成交场景实际成交 3 斤、使用 6 斤当日换券额度；禁用兑换时 0 成交。说明额度与部分成交仍由原整数规则决定。
- 新增 `tests/v019-payment-context.test.js` 4/4：三阶段报价等价、二分最大可付整数等价、上下文不进入 state 且真实成交重新核对、同户先收后付不使用跨卖家旧能力。

完整 state 对比覆盖家庭粮券/物资/收入/债权、镇库与店铺现金库存、交易账、换券额度、欠款和改革记录；因此本轮未引入额外资金或实物差异。
